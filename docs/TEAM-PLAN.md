# План команды и архитектура

## Идея

Не четыре отдельных приложения, а **одно окно-витрина**: слева список
рекурсивных задач, справа — визуализация, параметры и статистика. Каждая задача
живёт в своей папке Core и на своей странице Avalonia. Это даёт:

- единый стиль и одну точку входа на защите;
- минимум конфликтов в git — участники почти не пересекаются по файлам;
- возможность сравнивать алгоритмы: у всех одинаковые «шаги», «вызовы», «время»;
- общий каркас, который не надо переписывать каждому участнику.

Приложение намеренно разделено на два слоя:

```text
RecursiveLab.Core  — чистые алгоритмы и модели (net8.0, без Avalonia)
RecursiveLab.App   — окно, тема, страницы, отрисовка (Avalonia 11)
```

Алгоритм можно запустить и протестировать без окна. UI не содержит рекурсии —
он только рисует то, что вернул Core. Поэтому каждый участник может спокойно
переписывать «свой» файл, не боясь сломать чужую страницу.

## Роли

| Участник | Задача | Ветка | Файл |
|----------|--------|-------|------|
| 1 | H-дерево | `feature/htree` | `HTreeGenerator.cs` |
| 2 | Судоку | `feature/sudoku` | `BacktrackingSudokuSolver.cs` |
| 3 | Ближайшая пара | `feature/closest-pair` | `DivideAndConquerClosestPair.cs` |
| 4 | Ханойские башни (+ стек) | `feature/hanoi` | `RecursiveHanoiSolver.cs`, `StackHanoiSolver.cs` |

Перед сдачей замените «участник 1..4» на реальные имена в
`src/RecursiveLab.App/Services/LabTaskCatalog.cs` и в таблице выше.

## Git-флоу

1. `main` — всегда собирается и проходит тесты.
2. Каждый участник делает ветку `feature/<задача>` от `main`.
3. В ветке — только свои файлы (`Core/Tasks/<своя задача>`, тесты, свой `docs/TASK-*.md`).
4. Перед PR: `dotnet build` без предупреждений, `dotnet test` зелёный,
   ручной чек-лист задачи, скриншот страницы.
5. PR просматривает один другой участник (можно просто просмотреть diff и запустить приложение).
6. Merge в `main` — желательно squash, чтобы история была читаемой.

Подробные команды, подключение GitHub, защита `main` и CI — в
[`GIT-WORKFLOW.md`](GIT-WORKFLOW.md). Workflow `.github/workflows/ci.yml`
собирает Release и запускает тесты на каждый push/PR.

Коммиты: `feat(htree): ...`, `feat(sudoku): ...`, `fix(ui): ...`, `docs: ...`.

## Критерии готовности задачи

- [ ] Алгоритм реализован в своём файле Core и не меняет входные данные.
- [ ] UI-сценарий работает: кнопка запускает алгоритм, результат виден.
- [ ] Контрактный тест больше не пропущен (`Skip` снят) и проходит.
- [ ] Нет предупреждений сборки.
- [ ] Добавлен/обновлён `docs/TASK-*.md` (как запускать и что проверять).
- [ ] Скриншот страницы обновлён в `docs/screenshots/` (по желанию).

## Сценарий защиты (5–7 минут)

1. Открыть H-дерево, показать анимацию построения, подвигать глубину.
   Объяснить: `S(0)=3`, `S(d)=4·S(d−1)+3`, `O(4^d)`.
2. Открыть судоку, нажать «Решить». Показать, как заполняется доска,
   сколько шагов/вызовов сделал перебор с возвратом.
3. Открыть ближайшую пару: сначала «Перебор (эталон)», затем свой
   divide and conquer. Сравнить число сравнений расстояний при n = 2000.
4. Открыть Ханойские башни: запустить рекурсию, затем режим «стек».
   Показать, что число ходов `2^n − 1`.
5. Показать по очереди файлы алгоритмов: у каждого участника — свой файл,
   своя реализация, свой PR.

## Идеи для развития (если останется время)

- Экспорт фрактала в PNG (кнопка на странице H-дерева) для отчёта.
- Подсветка текущей строки псевдокода во время анимации (общий компонент).
- Дерево вызовов рекурсии для H-дерева и Ханоя (узлы = вызовы).
- График «время / количество точек» для ближайшей пары (перебор vs D&C).
- Пошаговая анимация судоку по `SudokuStep` (Try/Place/Remove).
- Светлая тема и настройка масштаба интерфейса.
- Горячие клавиши: пробел — play/pause, R — reset.
- CI (GitHub Actions): `dotnet build` + `dotnet test` на каждый push.
- Сохранение/загрузка условий судоку и наборов точек.
